# Breakage log

A running record of what actually broke, in order, with what it cost and what
fixed it. Started Day 1 of the revised roadmap.

**Why this file exists.** The final pitch has to say what went wrong, and a log
reconstructed afterwards from memory sounds like one — because it is one. Real
failures have specific error messages, wrong first guesses, and time costs.
Entries are appended as things break, never tidied up later.

Format: what broke → why → fix → cost.

---

## Day 1 — Wed 27 Aug 2026

### 1. Roadmap change stranded three days of finished work

**Broke:** Phase 4 M1–M3 (leak graph vocabulary, projection builder, and
observational patterns — ~1,700 lines with 932 passing tests) was completed and
verified against the old roadmap. The revised plan cuts the graph subsystem to
"four hours, one query, an evidence bundle".

**Why:** The old roadmap treated the leak graph as a headline deliverable. The
revised plan correctly identifies that a graph subsystem is not the
differentiator — incrementality measurement is — and that Razorpay already ships
detect-diagnose-retry.

**Fix:** Not deleted. The files are untracked and inert (nothing imports them),
so they cost nothing at runtime. `graph_builder.py` already walks a
`MerchantTimeline` and emits an ordered, deduplicated, causally sorted structure
— which is most of what the Day 8 evidence bundle needs. Decision deferred to
the owner rather than taken unilaterally.

**Cost:** ~3 sessions of work, partially salvageable. The lesson is the ordering
one: the measurement layer should have been built before the visualisation
layer, because the measurement layer is what the claim rests on.

### 2. Phase 1 metadata test asserts an exact table set

**Broke:** `test_all_expected_tables_registered` compares
`set(Base.metadata.tables) == EXPECTED_TABLES` by equality. Adding six tables
failed it immediately.

**Why:** The test was written in Phase 1 to catch tables added by accident. That
is a good guard; exact equality is how it works.

**Fix:** Extended `EXPECTED_TABLES` with the six new names rather than weakening
the assertion to a subset check. The guard keeps its strength and the growth is
recorded deliberately. Same reasoning as the Phase 3 Gate A correction, but the
opposite call — there, presence was the right intent; here, exactness is.

**Cost:** ~10 minutes.

### 3. Statistical parameters have no float-safe home

**Broke:** The revised plan specifies α = 0.05, power = 0.8, MDE, p-values, and
Qini coefficients. Every one is conventionally a float, and the schema bans
`Float` and `Numeric` outright — asserted by
`test_no_float_or_numeric_anywhere`.

**Why:** ADR 0001 banned floats for money and reproducibility. Statistical
parameters were not considered when that rule was written, but the reasoning
applies to them just as hard: a pre-registered α that compares inexactly across
runs is worse than useless.

**Fix:** Basis points for anything in [0, 1] or [−1, 1] — `alpha_bps = 500`,
`power_bps = 8000`, `mde_bps`, `ate_bps`, `qini_coefficient_bps`. For p-values,
basis points are too coarse (p = 0.00001 would round to 0), so
`p_value_micros` stores parts per million. Documented on the model.

**Cost:** ~20 minutes of design, and one genuinely better outcome than floats
would have given.

### 4. Autogenerated migration would have shipped without the lock guard

**Broke:** Nothing failed — which was the problem. `alembic revision
--autogenerate` produced a complete, correct 286-line migration, and the
pre-registration immutability guarantee was entirely absent from it.

**Why:** Autogenerate compares metadata to schema. A trigger is neither, so it
is invisible to the diff. The plan's phrasing — "the API must reject changes to
a locked experiment" — would have been satisfied by application code alone, and
that is a materially weaker promise: it holds only for callers that go through
the API.

**Fix:** Hand-wrote `revtrace_experiment_lock_guard`, a `BEFORE UPDATE` trigger
that raises when any frozen column changes while `locked_at` is set. The frozen
column list lives in one place and is built into the trigger body by the
migration, with a test asserting the model's list and the migration's list agree
— so adding a pre-registered field without protecting it fails loudly.

**Cost:** ~30 minutes. Verified by attempting the forbidden UPDATE in psql:

```
ERROR:  experiment 1111...1111 was pre-registered at 2026-08-27 22:15:01+05:30;
        its specification is immutable
CONTEXT:  PL/pgSQL function revtrace_experiment_lock_guard() line 16 at RAISE
```

### 5. Assignment attaches to a case that cannot yet cheaply exist

**Broke:** Not yet — flagged during schema design, before it could.

`case_assignments.case_id` references `recovery_cases`, and the plan says
assignment happens at case creation, immediately after detection. But
`recovery_cases` currently requires `risk_id` plus four NOT NULL money columns
(`expected_recovery`, `max_cost`, `estimated_cost`, `net_expected_recovery`)
that are Phase 6 concepts. Creating a case at detection time means filling them
with zeros before any recovery engine exists to compute them.

**Why:** `recovery_cases` was designed in Phase 1 as a Phase 6 artefact. The
revised roadmap makes it the unit of randomisation, which is a different job.

**Fix:** Deferred to Day 3, where the wiring happens. Options are (a) create the
case with zeroed projections and let Day 6 fill them, or (b) make the projection
columns nullable in a follow-up migration. (a) needs no schema change but stores
four zeros that are not measurements; (b) is more honest and costs a migration.
Recorded now so the choice is made deliberately rather than discovered under
time pressure.

**Cost:** 0 so far. Logged to stop it becoming a Day 3 surprise.

## Day 2 — Thu 28 Aug 2026

### 6. "Rebuild the simulator" collided with 1,587 passing tests

**Broke:** The revised plan says rebuild the simulator as a potential-outcomes
generator. `backend/tests/simulator/**` is 1,587 tests pinned to v1 behaviour —
including checksums — and is on the do-not-modify list.

**Why:** "Rebuild" read as "replace". Replacing `models.py`, `rng.py` or
`delivery.py` would have moved every recorded checksum.

**Fix:** v2 is **additive**. Every v1 module is byte-identical; the new modules
consume their primitives. `delivery.py` already produced duplicate, delayed,
out-of-order and dropped deliveries, so `webhooks.py` only had to add malformed
payloads. `GENERATOR_VERSION` stays `1.0.0`; v2 carries its own
`POTENTIAL_OUTCOMES_VERSION = 2.0.0`.

**Cost:** ~20 minutes of design, and a better outcome — the v1 scenarios remain
usable for the Day 8 case view.

### 7. `day_of_month` drawn 1..28 silently halved the salary window

**Broke:** Segment 2's whole mechanism is "responds only when retried after
salary lands". `SALARY_WINDOW_DAYS` spans 25–31 and 1–5, but the draw was
`randint(1, 28)`, so days 29–31 never occurred and a third of the responsive
window was unreachable.

**Why:** 28 was chosen to sidestep month-length handling. The interaction with
the salary window was not considered.

**Fix:** Uniform 30-day month, window trimmed to 25–30 and 1–5 — eleven of
thirty days. Documented as a deliberate simplification rather than left implicit.
Caught by computing the expected mixture by hand (0.367 × 4800 + 0.633 × 2200 =
3154) and checking it against the realised 3166.

**Cost:** ~15 minutes, and it moved the benchmark checksum, so the fixture was
regenerated.

### 8. Two isolation guards misfired on the word "harm"

**Broke:** `assert not any("arm" in name for name in fields)` — intended to
prove no case knows its assigned **arm** — flagged `harm0` and `harm1`. A second
guard rejected any attribute starting with `harm`, which flagged `RevealedCase.harmed`.

**Why:** Substring scans over names, for the third time in this project. The
same class of error as the Phase 2 hygiene guard and the Day 1 `executed` false
positive.

**Fix:** Exact field-name sets instead of substrings, and an explicit note that
`harmed` is a legitimately observable outcome — the realised harm under the
action actually taken — not ground truth. Only the *other* arm's outcome must be
absent.

**Cost:** ~10 minutes. Worth recording because the pattern keeps recurring:
name-substring guards are almost always wrong, and structural checks are almost
always right.

### 9. The dependency-direction test encoded the wrong allowlist

**Broke:** A new test asserted the simulator may import only `app.models.enums`
and `app.core.money`. It failed immediately: `simulator/config.py` imports
`DEFAULT_CURRENCY` from `app.models.mixins`.

**Why:** The allowlist was copied from `backend/README.md`, which is out of date.
The import is pre-existing v1 code and entirely legitimate — a string constant,
not an ORM class.

**Fix:** Inverted the test to assert on the *forbidden* side — no
`app.services`, `app.repositories`, `app.engine`, `app.api`, `app.db`,
`app.experiments`, `app.causal` — plus a separate check that no ORM model or
SQLAlchemy import ever appears. That states the actual rule instead of an
enumeration that goes stale.

**Cost:** ~10 minutes. The README allowlist is still wrong and should be
corrected on a documentation day.

### 10. Chained adjacent swaps drifted events two positions

**Broke:** The out-of-order emitter swapped `(i, i+1)` whenever a draw fired, so
two consecutive fires moved one event two places. A test asserting purely
adjacent transposition failed with `2 <= 1`.

**Why:** Real webhook reordering is local. Chained swaps are a different, easier
pathology than the adjacent transposition production actually presents.

**Fix:** Advance the index by two after a swap so pairs cannot chain. Maximum
displacement is now exactly one, and the test asserts it.

**Cost:** ~5 minutes.

## Day 3 (partial) — Fri 29 Aug 2026

### 11. The unit of randomisation was anchored to the wrong table

**Broke:** Not at runtime — caught during a pre-implementation inspection, which
is the only reason it was cheap.

Day 1 hung `case_assignments`, `case_outcomes` and `uplift_scores` off
`recovery_cases`. Two problems surfaced together:

1. **Seven tests assert `recovery_cases` stays at 0 rows after detection**, and
   two more assert `detection/service.py` and `risk_repository.py` cannot even
   *import* `RecoveryCase`. Creating a case at detection time to hang an
   assignment on would have made the project's central claim — detection
   identifies risk, it never authorises a response — false in substance.
2. **It would have broken intention-to-treat.** A `recovery_case` is created
   when the pipeline decides to act. Any unit that failed before that point
   would have had no assignment and would have silently left the denominator.
   That is selection bias, and ITT is the primary analysis in the
   pre-registration.

**Why:** The revised plan's schema sketch says `case_assignments.case_id` without
saying what it references, and `recovery_cases` was the table with "case" in the
name. `EXPERIMENT_DESIGN.md` had already defined the unit correctly — "a single
detected revenue risk on a single order" — which is a `revenue_risk`.

**Fix:** All three tables now carry `risk_id` referencing `revenue_risks`.
`recovery_cases` keeps its four `NOT NULL` projection columns exactly as Phase 1
shipped them: no nullable change, no zero placeholders, no migration against it.
A holdout unit now never gets a `recovery_case` row at all, which is a stronger
guarantee than the `holdout_never_acts` CHECK that remains as defence in depth.

**Cost:** ~40 minutes of inspection, ~30 of change. Both alternatives on the
table would have cost more later: zero placeholders would have put four
non-measurements into columns documented as "deterministic projections from the
recovery engine", and nullable columns would have forced a rewrite of
`estimated_cost <= max_cost`.

### 12. Amending a migration in place broke its own downgrade

**Broke:** `alembic downgrade` failed immediately after the amendment:

```
DROP INDEX ix_uplift_scores_risk_model
```

**Why:** Route 3a amends the Day 1 migration in place, which is safe only
because it is untracked and was never applied to `revtrace_dev`. But
`revtrace_test` *had* the old schema, so the amended `downgrade()` went looking
for `ix_uplift_scores_risk_model` while the database still held
`ix_uplift_scores_case_model`. The file and the database had diverged — exactly
the hazard the "never edit an applied migration" rule exists to prevent, in
miniature.

**Fix:** Non-destructive. Four `ALTER INDEX ... RENAME` statements brought the
database's object names in line with the amended file, after which the normal
`downgrade` / `upgrade head` cycle ran cleanly. No table was dropped, no row was
lost, and `revtrace_dev` was never touched — it stayed at `bbc0a1ffda2c`
throughout.

**Cost:** ~10 minutes. Worth recording as the concrete argument for route 3b:
amend-in-place is cheap only while every database holding the migration is
disposable, and it stops being cheap the moment one is not.

### 13. A covariate with no levels reported as balanced

**Broke:** `balance_report([])` returned `is_balanced = True` for `risk_type`,
`amount_band`, and `payment_method`.

**Why:** `CovariateBalance.flagged` for a categorical is
`any(level.flagged for level in self.levels)`, and `any(())` is `False`. An
empty population produces no levels, so "we checked nothing" and "we checked
everything and it was fine" rendered identically. The `Smd` type already had
the right rule — an undefined SMD is flagged — but the aggregate above it did
not inherit it.

**Fix:** A categorical with no levels is flagged, and a continuous covariate
with no `Smd` at all is flagged. An empty or one-armed population now flags all
five pre-registered covariates.

**Cost:** ~10 minutes, caught by the test that asserted the empty case.
Recording it because the failure mode generalises: every aggregation over
"is this suspicious" predicates has to decide what the empty case means, and
the safe answer for a diagnostic is always *not clean*.

### 14. The "balanced population" fixture was not reliably balanced

**Broke:** `test_a_balanced_population_is_reported_balanced` failed against a
200-unit fixture built by alternating arms and drawing amounts at random.

**Why:** Not a bug in the implementation — the fixture. With 100 units per arm
the standard error of an SMD is about `sqrt(2/100) = 0.14`, so a genuinely fair
draw exceeds the `|SMD| > 0.1` threshold roughly half the time. The fixture was
asserting that a coin came up heads.

**Fix:** Matched pairs — each drawn amount is given to one unit in each arm — so
the two arms hold identical distributions and every SMD is exactly zero.

**Cost:** ~5 minutes, and a useful calibration: the 0.1 threshold is not a
strict standard at experiment sizes RevTrace will actually run, which is an
argument for reporting the SMD table rather than reducing it to a pass/fail
badge.

## Day 4 — Sat 30 Aug 2026

### 15. A randomly drawn experiment id made the benchmark non-deterministic

**Broke:** Two runs of the same seed produced different arm assignments, and
therefore different estimates, while every visible sign said the run was
reproducible.

**Why:** The arm is `sha256(risk_id : experiment_id : salt)`. The population was
seeded and the risk ids were the generator's own case ids, so the *data* was
identical run to run — but `create_draft` allocates a `uuid4()`, so the
experiment id changed on every run and re-randomised the whole population. The
reproducibility that was actually checked (case ids, amounts, potential
outcomes) held perfectly, which is exactly why the failure was invisible.

**Fix:** The experiment and merchant ids are now `uuid5` derived from
`(seed, case_count)`. A test recomputes every stored arm with `decide()` and
matches both the arm and the digest, so the property is checked rather than
assumed.

**Cost:** ~25 minutes. The lesson is narrower than "test determinism": the run
had three sources of identity and only two were seeded. Partial determinism
looks exactly like determinism until something downstream depends on the part
that moves.

### 16. Preserved identity means a run cannot coexist with itself

**Broke:** A second `materialise()` in the same transaction failed with a
unique-constraint violation on `payment_attempts`, and would have failed on the
`revenue_risks` primary key immediately after.

**Why:** Not a defect — a consequence. The bridge sets `risk.id = case.case_id`
so the whole run is reproducible from the seed, and identity that is preserved
cannot be duplicated. Worse, a seed's populations are **prefix-stable**: the
first ten cases of a twelve-case run *are* the ten-case run, so even a different
`case_count` collides.

**Fix:** Two explicit guards with reasons, checked before anything is written —
one on the derived experiment id, one on the first case id, which is sufficient
because of the prefix property. An opaque `IntegrityError` became a sentence
explaining why the two runs cannot share a database.

**Cost:** ~10 minutes, and it removed a wrong test rather than adding a right
one: the test asserting "two runs assign identically" was asserting something
the design makes impossible.

### 17. A stray `and` in the report renderer, found by the line-length rule

**Broke:** `f"{report.recovery.rate_treatment_bps and _bps(...)}"` would have
rendered a bare `0` instead of `0.00%` for a treated arm that recovered nothing.

**Why:** Leftover from an earlier edit. No test caught it, because no test had a
zero treated rate — and at n=10,000 with a planted positive effect, none ever
would.

**Fix:** Removed. **Found by `ruff`'s 100-character limit**, which forced the
line to be split and made the expression readable. Worth recording because the
catch was incidental: the formatter surfaced a logic bug that the test suite was
structurally unable to reach, and the honest conclusion is that the renderer
needs a zero-rate case, not that lint is a substitute for tests.

## Day 5 (partial) — Sat 30 Aug 2026

### 18. Deterministic identity plus an open transaction is a deadlock

**Broke:** Two pytest runs of the Gray Zone module sat blocked for **1h40m**.
`pg_blocking_pids` gave the chain immediately once looked at:

```
 80752 | idle in transaction | blocked_by {}        <- root, 1h40m open
 87931 | active, ShareLock   | blocked_by {80752}   <- INSERT payment_attempts
 99544 | active, ShareLock   | blocked_by {80752}   <- INSERT merchants
```

**Why:** Two properties, each good on its own, combine badly. Case ids are
**prefix-stable**, so the first 4,000 cases of an N=10,000 population are
byte-identical to the N=4,000 population. And a module-scoped fixture holds its
materialisation in an **uncommitted** transaction for the module's lifetime. A
second materialisation on another connection then collides on
`uq_payment_attempts_provider_external` and waits.

The Gate 5 duplicate-run guard did not help, and could not: it reads with
`session.get`, which by design cannot see another transaction's uncommitted
rows. The guard catches a *sequential* rerun, never a concurrent one.

**Fix:** Removed the full-size contrast test from that module — it could only
ever deadlock against its own fixture. What it asserted is covered without a
second population: the ladder's preference for the fine cell is pinned in
`tests/causal/test_cells.py`, and the acceptance run reports the level split at
N=10,000 directly.

**Cost:** ~15 minutes to diagnose once `pg_stat_activity` was consulted, and it
was diagnosed only because the run was inspected rather than assumed slow. Two
lessons worth keeping. A guard built on `session.get` is a guard against
sequential mistakes only, and the docstring now says so. And a long-running
test is worth *looking at* — a 97-minute "slow" test was never going to finish.
